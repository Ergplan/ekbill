# Stage 5 — Wire: customers and items

**Status: built and tested in the build container; the independent review runs on the VM.** The customers, customer, customer-new, import, items and item screens read and write the database for a signed-in person; `?as=` looks (the /flow review and the Stage 1 baselines) stay on the fixtures, and every Stage 1 baseline is unchanged. The watcher is green through `drizzle-kit check`; `rules:check` stays red on the unverified count until `npm run rules:verify` runs on the VM (Stage 3's item); the steps after it were run one by one and are green.

## What exists

**Data model** (`packages/db/src/schema.ts` → `migrations/0004_customers.sql`): `customers` (name, contact_person, phone in E.164 unique per business when present, email, address, city, pincode, state_code, gstin, pan, language hi-Latn | en | hi | mr | gu | ta | te | kn | bn, language_source owner | guess, notes, archived, last_billed_at, import_row_id), `items` (name unique per business case aside, description, hsn_sac, unit, default_rate_paise, default_tax_bp, price_includes_tax, archived), and the import staging (I6): `imports` (status reading | ready | failed | committed, the per-file summary, added_count), `import_files` (the picked files as bytes, ≤ 8 MB each, audited without the bytes, never changed), `import_rows` (one candidate per customer found, the existing customer it matched, the customer the owner's tick made; the reading itself never changes). `apply_tenancy` on all five.

**Engine (pure)**: `customer.ts` (`checkCustomer`, salvaged from the MVP's `customer-form.ts`: GSTIN checksum, state and PAN derived, PAN-in-GSTIN, phone in E.164, PIN code, email, the reminder language; `fromGstin`; `offerLanguage`, which maps the salvaged `guessLanguage` to a reminder language and is offered, never applied), `item.ts` (`checkItem`: HSN 2/4/6/8 digits or SAC 6 digits starting 99, rate in paise, GST rate among the pack's selectable rates on the date; `lookupHsnSac` over `hsn-index.json` by code prefix or by words), `import/` (the MVP's `bill-text.ts`, `table.ts`, `markdown-lines.ts` salvaged unchanged in behaviour; `csv.ts` a quote-aware CSV reader in place of the MVP's csv-parse; `match.ts` the MVP's `matchExisting` and `dedupeWithin`).

**Worker** (`apps/worker/src/import/`): `read-file.ts` (salvaged: the PDF text layer through pdfjs-dist, CSV, XLSX without a library (`xlsx.ts`), Docling for photos, scans and PDFs whose text gave nobody; a sentence for every file that gave nobody), `docling.ts`, `job.ts` (`read-import`: reads an import's files for the person who started it, as the system, and records the staging rows). The worker now runs with React's server condition (`tsx --conditions=react-server`), because the db package guards itself with `server-only`; the compose command and CI start it that way, and Playwright starts it beside the dev server.

**Repositories**: `repos/customers.ts` (list with search, get, create, update, archive; `existingForMatch`), `repos/items.ts` (list, get, create, update, archive), `repos/imports.ts` (`startImport`, `filesOf`, `recordReading`, `failImport`, `getImport`, `commitImport`). Roles: staff add and change customers and items and run imports; only the owner archives (nothing is deleted); the accountant reads. `commitImport` adds only the ticked rows that are not already customers, in one transaction; a phone that turns out to belong to a customer links rather than duplicates; a field the check refuses is dropped rather than the row.

**Web**: `POST /api/imports` (multipart, owner and staff, 20 files of 8 MB; stores the import and queues `read-import` through `server/queue.ts`, a send-only pg-boss client), `actions/people.ts` (`saveCustomer`, `setCustomerArchived`, `saveItem`, `setItemArchived`, `commitImport`), `screens/people.ts` (row → the fixture shape the screens draw), async loaders for the six screens. The seed puts the fixture customers and items in the database with ids derived from their fixture keys, so the still-fixture bills (until Stage 6) find their customer's row and the customer folder shows its bills.

**Screens**: the directory lists the rows with search; the folder shows a row with its language by name; Naya customer saves the row (the language offered from the surname, e.g. "Patil — Marathi mein bhejein?") and goes to the bill; the item screen saves with the HSN/SAC lookup sheet; the import screen uploads, waits on the worker (the page asks again until the import is read), shows each customer found with where it was read from and "Pehle se hai", adds the ticked ones, and says why a file gave nobody.
